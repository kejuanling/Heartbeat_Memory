# 最高行动准则

1，接到需求，先理解，复述（先说你的想法，实现计划，以及认为这个实现怎么用，有什么用），与用户确认是否理解对，并一句话列出预计修改的文件。错误案例：自以为理解，直接开干。
2，需求问题不清楚的直接问用户。错误案例：觉得用户不想被问，按猜测直接开干。
3，执行任何任务前，先拉取最新服务器代码到本地，执行前先备份文件，完成任务以后等用户验收，验收完成以后统一清理无用文件、脚本、备份，提交git，并自行完成会话总结流程。错误案例：直接修改本地文件直接推送导致文件覆盖、留一大堆无用文件在服务器或本地、无效代码不清理留在那误导后来看的人、只更新代码不更新注释。
4，执行单个任务之前、之后检查是否有连带、相关的功能、逻辑受到影响。错误案例：说改就只改这一行代码，不看可能有关联的代码，直接收工结束。
5，如果在任务中被一些注释、死代码、旧代码影响判断，先记下来，等完成任务以后告诉用户，询问是否检查、更新、清理。

## 失败经验（行为层，非技术命令）
> 本节记录**因判断/流程失误导致的高阶行为教训**，不记录具体命令坑（命令坑统一去 `02`）。

- **别信任静默成功**：脚本/服务重启要捕获退出码并确认，别只看“执行了”。
- **覆盖前先真备份**；别用 `-f`/`-y` 假备份，也别覆盖后才发现没留原版。
- **改完语法检查再 reload**：配置改了但不 reload/重启，等于没改。
- **别依赖“上一轮的缓存/旧副本”**：真值以远端/最新为准；工具结果不一定跨轮保留，要查就重查。
- **“加一个“往往是想多了，先问用户要不要单独的“通用/最小”工具**：需求方常只想要一个**最小的、单一职责**的工具，不要自作主张加前缀、多个专用工具或耦合逻辑。改工具前先用选择题确认。
- **系统级目录与文档路径不一致时以 systemd/实际为准**：改服务前先 `systemctl cat <服务>` 拿真实 `WorkingDirectory`+`ExecStart`，别按文档路径找文件。
- **注入上下文先过目**：任何会直接注入 AI 上下文的内容（提醒/备忘/系统提示/记忆/特殊事件等），实施前必须把**注入位置和渲染后的完整实际内容**拿给用户确认，问清是否要改、怎么改，确认后才推送上线——防止上线后返工。

## 会话总结流程

1. **不新建独立文件**：直接打开当天 `agent每日工作记录\工作记录_YYYY-MM-DD.md`（没有就新建），在**开头**（标题之后、旧内容之前）**插入**会话总结；**最新在上、倒序排列**（越新越靠前）。**每条会话总结的标题必须带当日序号 id `MMDD-NN`**（如 `0904-01`、`0904-02`……`NN` 为该记录在当天的第几次写入，从 `01` 起递增；当天现有条数+1 即新 id）。插入格式如下：
   ```markdown
   ## 会话总结：<MMDD-NN> <一句话主题>
   > 时间：<时段>。承接：<上一主题 / 若无>。
   ### 1. 干了什么（一句话）
   ### 2. 改动清单（文件 · 改了什么 · 是否已推送/生效）
   ### 3. 关键决策与理由、代码逻辑。
   ### 4. 验证结果
   ```
2. **总结后清理检查清单**（按顺序逐项核对）：
   - **失败经验**：本次会话是否有过失败返回结果？若有，项目专属业务逻辑坑直接记到 `00_每日记录目录.md` 对应条目的「踩坑：」标注（技术命令/环境坑记到 `02_本地Agent工作方法.md`）；若没有则补充记录。
   - **遗留事项**：本次会话是否完成了 `05_遗留事项_待接手.md` 中的条目？若有，从 `05` 中删除该条目，完成细节只在当日工作记录中归档。
   - **目录索引**：是否在 `agent每日工作记录\00_每日记录目录.md` 中追加了当日会话总结的索引项？
   - **清理临时文件**：本次会话是否产生了无用备份、临时脚本、测试文件？若有，清理或明确保留理由。
   - **系统变更**：是否在服务器上做过代码/配置更改？若有，`03_系统介绍.md`（静态路径/端口/路由/目录结构）是否需要同步更新？需要则更新。
是否提交了git？
3. **每日记录同步服务器**：每天定时23：00同步。
