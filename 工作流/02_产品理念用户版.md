# 02 产品理念（用户版，非必读，偶尔翻）

记一些我需要记住的功能设计决策。不是技术实现，是"为什么这么做"。

## 日记系统

**写入两条路**：
- AI 在回复末尾写 `[DIARY]...[/DIARY]` 标签块
- AI 调 write_diary 工具写

**落盘**：
- 日记正文存 `data/diary.json`（单 JSON 文件，id 按创建顺序自增，不回收）
- 时间线追加一条 `kind:diary` 的隐藏 assistant 消息，content 是 `[DIARY]...日记全文...[/DIARY]`
- 普通 assistant 消息落原始完整文本（含 [DIARY] 块），不剥任何东西——后端时间线是流水账

**在 AI 上下文里**：
- kind:diary 消息作为一条 assistant 消息发给 AI，AI 能读到完整日记
- kind:diary 消息不被压缩（isDiaryEvent 保护），时间线文件里永久原文存在，不被概括
- 跨窗口注入有篇数限制（最近 N 篇），时间线上的日记只要不删就一直存在
- 窗口滑出的老日记不每次都发，靠日记检索工具/跨窗口注入按需调取

**在前端**：
- 聊天界面显示时剥掉 [DIARY] 块，用户看不到标签和日记正文
- history API 下发原始 content，剥标签在前端 stripInnerTags 做
- 点编辑时编辑框填原始 content（含标签），方便检查核对
- kind:diary 消息 history API 过滤掉，前端不显示

**hidden=true 的日记**：
- 不注入上下文
- 不参与跨窗口注入
- 日记检索工具也检索不到
- 和删除等效，只是用户可以在日记页恢复显示


## 相关记忆注入（Possibly Relevant Memories）

**为什么做这个功能**：聊天时 AI 应该记得"最近发生过的具体的事"，聊到相关话题能接上话。之前做过一版"按意思相近捞记忆"，结果老把不相关的也捞进来，感觉不聪明，就下线了。现在重做，改成**靠关键词命中 + 语义补一点**，少而准。

**记忆分三类**：
- fact：关于人的稳定特质（她学什么专业、喜欢什么口味）
- rule：规则、边界、承诺（回复不要用 emoji、以后不要提某件事）
- event：具体发生过的一件事 / 做出来的东西（"她做了一个网页，域名是 xx"、"上个月我们一起去看了海"）——之后聊天可能还会引用

**每条记忆都带**：
- 关键词（1-6 个）：这条记忆的"门牌号"，聊天里出现这些词（或她的口语说法）就能把它捞出来。短记忆一个词就够，长的可以多个，最多六个。关键词不光是字面词——先选原话里的代表词保底，再补一两个她可能会随口说的说法（比如记忆是"她会速画速写"，除了"速写"还补"画画"，她哪天说"今天想画画"也能捞到这条）；原词够用就不强行补，别泛化成"艺术""创作"这种太宽的
- 氛围（可选）：这条记忆给 AI 的感觉（温暖、紧张、雨夜的潮湿感、海盐味）——用来判断"语境搭不搭"。没有明显感觉就不打
- 来源：这条记忆是从哪个对话里来的

**注入规则**：
- 只捞 event（一件事）。fact 和 rule 是"对人"的，开头两段固定注入就够了；event 是"对事"的，按当前话题浮动补充
- 打分 = 关键词命中×0.5 + 语义相关×0.15：关键词字面撞上了分高，意思相近的靠语义补一点
- 每轮只注入分最高的那条，最多一条
- 分太低（低于 0.3）不注入——宁缺毋滥
- 这件事本来就发生在当前这个对话里的，不重复注入（AI 刚才已经看到了）
- 氛围的作用是拦截：字面撞了关键词但语境完全不搭的，不捞

**event 会过时，所以有衰减**：
- 每次被注入，它的价值分涨一点
- 很久没被聊到，价值分慢慢降
- 降得太低（20% 以下）就移出主池，进待审，等处理
- 老记忆重跑整理时顺手更新价值分

**记忆入库时**：AI 要分清什么是一次性琐事（吃了什么、寒暄——不记），什么是值得记住的具体事（做了个网页、一次重要的经历——记成 event）。"气氛"不是用户自己说的，是 AI 感受到的氛围。

**管理台**：
- 每条记忆卡片能看到它的关键词和氛围
- 有个"相关记忆注入"配置区：权重、门槛、条数、衰减快慢，全部手动可调
- 有个"注入预览"：显示最近几轮本应注入哪条、分多少——上线前先用它观察准不准

**上线节奏**：存量老记忆全部重跑补好关键词、氛围、分类之前，不开启注入；等重跑完、预览观察准确了，再正式开。
## 记忆链路：谁在干活（大白话版）

一条记忆从产生到用起来，走一圈六个环节：

1. **蒸馏（捡）**：AI 每天看完对话原文和日记，挑出值得长期记住的原子记忆——分类（fact/rule/event）、打关键词、可选的氛围、标明来源。它只管捡，不打价值分。

2. **门卫（打分，不拍板）**：给每条候选打两个分——价值分（这条值不值得留，0-1）和时效分（这条会不会过时），各带一句理由。它不决定留不留：打低分也只是"交人工"，从不自动拒绝或合并。

3. **重跑（回锅）**：把池子里已经存着的旧记忆每隔一段重新过一遍——重新分类、补关键词、补氛围、顺手更新价值分。补完的标签再过一次门卫打分。所以门卫用两回：蒸馏出新的走一遍、重跑翻旧的再走一遍。

4. **两块总结（造人设底色）**：池子里的 fact 和 rule 分别被汇总成两块常驻文本——"规矩"（rule：边界、承诺、交互约定）和"理解"（fact：她的稳定特质）。每次对话开头都带着，AI 长期记得"她是什么样的人、有什么规矩"。

5. **相关注入（临场捞事）**：只捞 event。聊天聊到相关话题时，按混合分临时捞一条最相关的具体事补进上下文。纯算法，不调模型，每轮最多一条。

6. **记忆检索（AI 主动查）**：AI 拿不准时主动查记忆池（memory_search 工具）。它也走混合分，但类不限制（fact/rule/event 都能查）、最多返回 5 条。AI 用完整一句话问（"她上次说想学画画那件事"）比丢两三个关键词更容易命中——短词只做字面匹配，一句话会带意思相近的匹配。

**为什么分两拨**：fact/rule 是"对人"的稳定底色，固定常驻就够了；event 是"对事"的，平时不占上下文，聊到相关话题才临时浮现。所以只有 event 走"临场捞"这一套。

**节奏**：存量老记忆全部重跑补好标签之前，不开启注入；重跑完、预览观察准确了，再正式开。

## 日记在时间线里的位置

- kind:diary 消息放在状态机压缩摘要**前面**，不是落在压缩块覆盖范围内
- 原因不是防被摘要吞掉（isDiaryEvent 本来就保护），是为了前缀缓存命中——日记这段固定内容不变，放在压缩摘要前面，网关增量缓存命中率更高
- 补写老日记时，如果该日记原文落在 state 块覆盖范围内，kind:diary 消息要插到 state 块之前，不要插在范围内


## 上下文快照（前缀缓存，1007 拍板 · 1008 修订）

**为什么做**：每次请求都重新组装整个人设、工具定义、历史消息（含状态块/摘要块），大部分内容落盘后其实不变，白算。参考主流 AI 应用的做法：把不变的前缀固化成快照落盘，每次请求直接复用，只有尾部动态拼。

**重要边界（1008 补）**：快照解决的是**省算/省钱**（命中上游 prefix cache），**不是减少消息条数**。条数下降是**状态机摘要**的职责——状态机覆盖区间往前走，原文才被替换成摘要。快照前缀里装多少条，请求就发多少条（加尾部）。这两件事别混。

**快照是什么**：从会话第一条消息开始，把「人设 + V2 注入块 + 工具定义 + 历史消息（含状态块/历史摘要块/记忆浮现/特殊事件/工具记录）」全部固化进快照文件 `data/session_ctx_snapshots_v2/<sessionId>.json`。快照里的东西**全部冻死**——除非重建事件触发，否则永远不变。

**快照存什么（1008 第四步 · 方案A 定稿）**：快照 = **冻结内容**（`content` 数组：普通消息存完整消息副本；`_ctxRep` 摘要块连内容+repId 一起存）+ **快照点**（`snap_point`：时间线数组下标，尾部起点）。读取 = 冻结 content + 时间线 `slice(snap_point)` 之后的消息现算拼接，**读取路径无任何写操作**。

- 相比第三步「存 id 列表」：id 差集算尾部会把 rep 块（无 id）替代的原文**永远当尾部捞回并永久追加**（P0：主会话 entries 膨胀到 660 条 id + 1 个 rep，摘要与全量原文常驻并存，压缩实际失效）——冻结内容 + 下标尾部不会有这个问题：rep 块替代的原文根本不在 content 里，尾部从快照点起干净截断。
- 时间线被缩短（清尾/删除尾部）时 `snap_point` 收缩防错位——旧结构「下标一旦超过缩短后的时间线就永久错位、连尾部并入都不再执行」的根因，v3 天然自愈。

**请求 = 快照（前缀） + 动态尾部**：每次发送时，冻结 content 直接读盘复用，尾部 = `timeline.slice(snap_point)` 现算拼接（含本轮最新 user + 相关记忆 + 容量提醒）。tools 直接用快照里的，不再每次拉 MCP。新消息落盘 = 进尾部，**不需要并入快照**（snap_point 不变，slice 自动包含）。

### 触发重建 / 截断的事件（1008 方案A 定稿）

**全量重建（markStale，下次请求懒生成新快照）**：
1. 状态机摘要更新（`/admin/conversation-state` commit / edit / rollback）
2. 历史摘要更新（`/admin/context-replacements/update`、restore 恢复历史版、手动块保存）
3. 压缩块启停 / 隐藏 / 撤销（toggle / hidden / undo —— 块冻结在快照 content 里，不重建则改动永远不生效）
4. 手动重建：聊天端会话菜单「重建快照」（1008 已修复：此前调旧 context-snapshot，v2 快照文件纹丝不动 = 点了没效果；现在改删 v2 快照+清失效） / 管理台重建

**截断（不重建，保留前缀 token）**——编辑 / 删除 / 重新生成落在 content 区且**其后没有压缩块**时：
- 冻结 content 截到该消息之前，`snap_point` 缩到该消息位置，之后的消息走尾部现取（前缀 token 缓存保留）
- 其后还有压缩块 → 全量重建（避免摘要丢失、区间原文全量回流）
- 落在尾部区（`snap_point` 之后）→ 什么都不用做（尾部本来就现取）

**压缩块区间内禁改**：落在任一可见压缩块区间（状态块 / 手动块）内的消息，编辑 / 删除 / 重新生成一律拒绝（接口回错误提示）。

**其他一律不重建（等你手动）**：
- 工具定义变化：继续用快照里的旧的
- 人设 / V2 块变化：继续用旧的
- 标星变化：不重建（位置冻结，重建后重新生效）

### 可编辑内容的版本标识（gitid = 身份 + 内容指纹，1008 第二步）

凡"能被编辑"的东西都带版本标识，内容一变标识就变：

| 对象 | 字段 | 形式 |
|---|---|---|
| 人设 system prompt | `spRev` | `sp:<backupId\|global>:<hash8>` |
| 日记 | `diaryRev` | `diary:<diary_id>:<hash8>` |
| 记忆注入块 | `repId` | `<item.id>:<contentRevHash>` |
| 快照本体 | `sp_rev` | 诊断留痕，读取仍用快照冻结的人设内容 |

`contentRevHash` = sha256 取前 8 位。以上字段均被 `sanitizeForUpstream` 剥离，**不发上游**。

### 标星（1008 第一步）

- 标星键从"内容 sha256"改为**优先用 `msgid`**，兼容存量内容键（双查：先 id、再回落内容键）。
- 标星 / 取消标星**都不触发重建**，只在状态机压缩时生效。
- 标星**不影响**发给状态机 LLM 的上下文；已标星的 msgid 放在状态摘要前。

### 为什么工具定义也冻死

每个工具编辑一下，如果跟着重建，整个前缀缓存就全废了。工具定义变了就让它旧着，等找时机手动重建一次。

### 位置原则

状态块 / 历史摘要块在快照里的位置和现在实际请求里完全一致（按时间线锚点内嵌），不改变结构。

### 失效标记与重建的边界（1008 排查补充）

- 失效标记是 `data/session_ctx_snapshots_v2/.stale-<sid>.json`，快照重建成功后自动清除；**没有该文件 = 对应重建事件从未真正执行**（可用于反查状态机是否并过）。
- **重建快照 ≠ 上下文变小**：重建走增量 head（"有块区间摘要化、无块区间原文透传"）。状态机覆盖区间没连成一片时，未覆盖段全部原文透传，重建后上下文不会变小、反而暂时变差。想让上下文真正瘦下来，唯一的办法是让**状态机覆盖区间连成一片并往前压**。
